# ADR-008: Reviewer independence through job, context, model, prompt and permissions (D8)

**Status:** Proposed (2026-11-24)

## Context

The assignment requires that the reviewer sees only the issue, the diff and the repository at the PR head; that it can run code but not push; and that it does not simply agree with the implementer. LLM reviewers are known to approve fluent changes, especially when they are shown the author's explanation.

## Decision

Independence is enforced at five layers:

1. **Own job.** The review job checks out `refs/pull/N/head` fresh and never downloads the build artifacts.
2. **Own context.** Inputs are exactly: the issue (fetched from GitHub, wrapped as untrusted), `git diff origin/<base>...HEAD`, and the repo. The PR description (written from our artifacts) is not passed.
3. **Own model.** Sonnet 5.5 instead of the builder's Opus 5.5 (ADR-006).
4. **Own prompt, built against rubber-stamping.**
   - The reviewer starts from the issue and must list what the issue asks for *before* reading the diff.
   - It must run the test suite and try at least one input of its own that is not in the new tests.
   - Every finding needs file:line plus the command it ran and what it saw.
   - It returns a structured verdict (`--json-schema`): `approve` requires every checklist item to be true.
   - It is told that the change was produced by an automated agent and has an estimated prior chance of being wrong.
5. **Own permissions.** Job token `contents: read`; no token in the agent environment; no push. Writes the reviewer makes stay in the throw-away runner.

The route job posts the review. It rejects a `request_changes` verdict with no evidence-backed finding, and an `approve` whose checklist has a false item (treated as `request_changes`).

## Alternatives considered

- **Same session reviews its own work:** cheapest, but not independent.
- **Reviewer gets spec/design/test report:** easier review, but adopts the builder's framing; a wrong spec would go unnoticed.
- **Reviewer can push fixes:** faster convergence, but merges the reviewer and implementer roles.

## Consequences

- Good: the reviewer can catch a wrong *interpretation* of the issue, which no earlier check can.
- Bad: without the spec, the reviewer may judge against its own interpretation of a vague issue.
- To test: experiment E1 (same model + builder context vs. this design) on five seeded PRs with known defects.
