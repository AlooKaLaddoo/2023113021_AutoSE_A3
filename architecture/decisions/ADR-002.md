# ADR-002: Deterministic state machine inside a job; review rounds re-dispatch the workflow (D2)

**Status:** Proposed (2026-11-24)

## Context

The flow has loops: failing tests go back to implementation (or design), and review can send work back to design or implementation. GitHub Actions jobs form a DAG and cannot loop. An LLM "planner" could decide the next step, but then the most important control decisions (when to stop, how many retries) would depend on a model that may be manipulated by the issue text or simply be wrong.

## Decision

- Stages 1-4 run inside **one `build` job** driven by `orchestrator.py`, a small **state machine in Python**. States are `requirements → design → implementation → testing → done | failed`. The transitions are fixed in code:
  - a stage check fails → retry the same stage once with the check output;
  - testing fails → back to implementation (max 3 attempts per design);
  - two failed implementation attempts → back to design once;
  - any budget exhausted → `failed`, with the reason written in the current artifact.
- Release, review and routing are **separate jobs** (`release → review → route`) so they can have different permissions (ADR-005, ADR-008).
- A review that requests changes is turned into a new run by the `route` job: `gh workflow run autose.yml -f issue=N -f round=R+1 -f from_stage=design|implementation`. The **reviewer proposes** the route (`verdict.json`), the **route job (code) decides** whether rounds are left.

## Alternatives considered

- **LLM orchestrator with worker agents.** Flexible, but stopping and budgets would rest on model judgement; harder to explain and to test.
- **Every stage as its own job, chained with `needs:`.** Clean permissions per stage, but loops 3↔4 cannot be expressed, and each job pays the setup cost (checkout, Python, CLI install, ~1 min).
- **Jobs triggering each other through `repository_dispatch` for every stage.** Possible, but turns one run into many runs that are hard to follow.

## Consequences

- Good: the control flow is ordinary code that can be read and unit-tested; the agents never decide when to stop.
- Good: a full round is one Actions run; each review round is one more run, linked from the state comment (ADR-004).
- Bad: stages 1-4 share one job, so they share its permissions (`contents: read` only, which is acceptable).
- Bad: a run that is cancelled mid-job loses its in-job state; see ADR-004 for restarts.
