# ADR-001: Four agent roles, not one agent and not one per stage (D1)

**Status:** Proposed (2026-11-24)

## Context

The six SDLC stages are fixed. Each stage needs different knowledge and different powers. Requirements and design only need to *read*. Implementation needs to *edit and run*. Testing must check the implementation, and review must be independent of everything before it. Running one Claude Code session for all stages is the cheapest option and keeps every detail in one context, but then the same reasoning that wrote the code also writes the tests and judges them, so its mistakes get confirmed instead of caught. Six agents, one per stage, maximise separation but add hand-offs, and the release stage does not need judgement at all.

## Decision

Use **four LLM roles plus deterministic code**:

| Role | Stages | Why grouped like this |
|---|---|---|
| Analyst | 1 Requirements, 2 Design | Both are read-only reasoning about *what* and *where*. The design must follow the spec closely, and the same role prompt (A1 skill + `ARCHITECTURE.md`) covers both. |
| Implementer | 3 Implementation | The only role that edits product code. |
| Tester | 4 Testing (writing the acceptance tests) | Writes tests from `spec.md` alone, in a clean checkout of the base commit, so its tests are not shaped by the implementation. |
| Reviewer | 6 Review | Separate job, separate model (ADR-008). |

Stage 5 (Release) and every check are **plain code**. Pushing a branch and opening a PR has one correct way to be done and gains nothing from an LLM. A small Haiku "judge" is used only inside the stage 1 check (ADR-007) and is not counted as an agent.

## Alternatives considered

- **One agent for stages 1-4** (e.g. a single `claude -p` "fix this issue"). Fewer tokens and no hand-off loss, but tests written by the implementer tend to mirror the code; no artifact boundary can be checked mid-way.
- **One agent per stage (6 agents).** Requirements and design would be split, although the design agent then re-reads the whole spec and the repo; the release "agent" would be an LLM wrapped around three `gh` commands.

## Consequences

- Good: the implementer cannot "grade its own homework". Tests come from a different session that never saw the diff.
- Good: three of the four roles have no write access to product code.
- Bad: the Tester may misread the spec and write a wrong test; the implementer then cannot make it pass. This is bounded by the retry budget (ADR-009), and the failure appears in `test_report.md`.
- Bad: more sessions mean more repeated repository exploration (tokens).
- To test: experiment E2 compares "Implementer writes its own tests" against this design.
