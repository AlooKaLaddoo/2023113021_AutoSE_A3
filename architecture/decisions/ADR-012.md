# ADR-012: An unverified review is "inconclusive", never an approval (D7, D8)

**Status:** Accepted (2026-11-24). Supersedes ADR-008.

## Context

ADR-008 made the reviewer independent at five layers (own job, own context, own model, own prompt, own permissions) and had the route job validate the reviewer's structured verdict. Its validation rule was: "reject an `approve` whose checklist has a false item; treat `request_changes` without an evidence-backed blocker/major finding as approve with comments".

**Run [45419585282](https://github.com/AlooKaLaddoo/markdown/actions/runs/45419585282)** showed the hole. The reviewer could not run any command (sandbox failure, ADR-011). It correctly answered `request_changes`, with `existing_tests_pass = false` and `own_probe_done = false`, and only a `minor` static finding. Our rule turned that into **approve**. In other words, the code that was meant to stop rubber-stamping produced one. The reviewer itself had been more careful than our rule.

## Decision

The five independence layers of ADR-008 remain unchanged. The orchestrator's decision rule is replaced by:

| Reviewer output | Orchestrator decision |
|---|---|
| ≥1 `blocker`/`major` finding with evidence | `request_changes`; route = reviewer's route (`implementation` if it gave `none`) |
| no such finding, **every** checklist item true | `approve` (even if the reviewer said `request_changes` with only minor findings) |
| no such finding, some checklist item false (e.g. tests not run, no own probe) | `inconclusive`: post the review, stop, a human decides; no loop-back |
| no valid structured output | `inconclusive` |

Approval now needs positive evidence that the reviewer actually ran the suite and its own probes. The absence of findings is no longer enough.

## Alternatives considered

- **Trust the reviewer's own verdict field:** in this run it would have been right, but then a reviewer that says "approve" without running anything would pass too.
- **Retry the review automatically when inconclusive:** useful for transient failures, but it can mask a systematic problem such as the sandbox. We prefer that a human sees it.

## Consequences

- Good: an infrastructure failure on the reviewer side can no longer produce an approval.
- Good: re-run on the same PR after the sandbox fix ([45420028911](https://github.com/AlooKaLaddoo/markdown/actions/runs/45420028911)): the reviewer ran 1168 tests and its own probes, and approved with every checklist item true.
- Bad: one more terminal state for maintainers to handle.
