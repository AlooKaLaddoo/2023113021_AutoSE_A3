# ADR-006: Opus 5.5 builds, Sonnet 5.5 reviews, Haiku 5.5 judges (D6)

**Status:** Accepted with caveat (2026-11-24): experiment E1 found the same defect catch rate for an Opus reviewer; the different model is kept for cost, not as the cause of independence (report §3). Proposed 2026-11-24.

## Context

Constraint: the team does not want to pay per token. The workflow therefore runs on a Claude Team subscription through a `claude setup-token` OAuth token (`CLAUDE_CODE_OAUTH_TOKEN`), which has usage limits instead of a bill. Cost is then measured in tokens and in plan usage, not dollars. Ability matters most where the work is hardest (unfamiliar codebase, design, code). Review benefits from a *different* model: two runs of the same model share blind spots. Small classification checks do not need a large model.

## Decision

| Role | Model | Reason |
|---|---|---|
| Analyst, Implementer, Tester | `claude-opus-5-5` | Strongest Opus-tier coding model available on the plan; A2 showed Opus 5.5 completes Python-Markdown tasks reliably |
| Reviewer | `claude-sonnet-5-5` | A different model than the builder, so its errors are less correlated with the builder's; fast and cheaper in plan usage |
| Spec testability judge | `claude-haiku-5-5` | A yes/no classification per acceptance criterion; small model is enough and fast |

API list prices (for the token report; not billed here): Opus 5.5 $4/$20, Sonnet 5.5 $2/$10, Haiku 5.5 $0.10/$0.50 per million input/output tokens.

## Alternatives considered

- **Opus 5.5 everywhere.** Simplest; reviewer independence would rest only on prompt and context. Tested as a variant in experiment E1.
- **Fable 5.2 as reviewer.** Most capable model, but roughly 4x Sonnet's usage weight; not justified before measuring.
- **A paid API key.** Excluded by the budget constraint.

## Consequences

- Good: $0 marginal spend; tokens are still reported from the CLI's usage output.
- Bad: subscription usage limits can interrupt a run (rate limit). The orchestrator records this as a stage failure with the reason, and the run can be restarted.
- Bad: a weaker reviewer than the builder may miss subtle bugs; E1 measures this on seeded PRs.
