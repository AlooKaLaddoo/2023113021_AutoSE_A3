# ADR-007: Checks are code first; an LLM judges only what code cannot (D7)

**Status:** Proposed (2026-11-24)

## Context

Each stage has a fixed check. An LLM judge can assess anything but can be persuaded, varies between runs, and costs tokens. Code checks are cheap and repeatable but can only check structure.

## Decision

| Stage | Check | Kind |
|---|---|---|
| 1 | Every FR has ≥1 acceptance criterion with ID `AC-FR-xxx-yy` and non-empty Given/When/Then; no requirement `BLOCKED_ON_CLARIFICATION`; then each AC is classified testable/untestable by Haiku | code + LLM judge |
| 2 | A "Change plan" table lists `file | symbol | change`; each file exists or is marked `new`; each symbol is found by `ast` in that file or marked `new` | code |
| 3 | Diff non-empty and inside the file allowlist; `pip install -e .`, `python -m compileall -q markdown`, `python -c "import markdown"` | code |
| 4 | Each AC ID maps to ≥1 test named `test_ac_fr_xxx_yy*`; `python -m unittest discover tests` passes (old + new) | code |
| 5 | PR is `OPEN`; dispatched `ci.yml` run concluded `success` | code |
| 6 | Reviewer verdict validated against a JSON schema; `request_changes` must carry ≥1 finding with evidence | LLM + code validation |

**The orchestrator (code) makes every pass/fail decision.** The LLM judge only supplies one input to the stage 1 decision; the reviewer only supplies a proposal to the route job.

## Alternatives considered

- **LLM judge for every stage** ("is this design good?"): flexible, but agents tend to approve fluent text, and results vary between runs.
- **Only code checks:** "testable" cannot be decided by a regex; a criterion like "headings should look nicer" passes any format check.

## Consequences

- Good: checks are cheap, deterministic and visible in the artifacts.
- Bad: structural checks can be satisfied by a wrong plan (right file names, wrong idea). Only tests and the reviewer catch that.
